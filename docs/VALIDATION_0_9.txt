NEW WORKFLOW BEHAVIOR EXERCISED

1. Initial setup hides the simulation controls, operating tabs, unit tree,
   object inspector, message dock and session status bar.
2. Hidden navigation, shortcuts and direct operating commands cannot bypass
   the vehicle and workspace stages.
3. Editing a draft makes no vehicle mutation. A rejected draft stays visible
   with an error and does not replace the previous model.
4. Repeated Continue submissions commit one vehicle. A complete state/resource
   response means there is no dependency on follow-up metadata GET requests.
5. Back followed by unchanged Continue keeps the prepared vehicle without
   another configuration request.
6. Entering Drive or service does not recreate the vehicle.
7. Switching workspaces preserves the same clock, history, faults, selected
   object, recorded signals and diagnostic records.
8. Unit map, signals, wiring and locations remain linked under service.
9. Service's Vehicle configuration page shows the shared fitted hardware;
   its Edit action opens the single global vehicle editor.
10. Change vehicle pauses the run and releases held driving controls. Cancel
    returns to the current session paused, retaining its data and selection.
11. Cancelled draft values are discarded before reopening the editor.
12. Applying changed settings resets once and returns to the previous activity.
13. A lost configuration response blocks cancellation and operation until an
    explicit retry confirms the vehicle, even if the draft matches the old one.

The setup integration suite additionally enters Diagnostics & service directly,
switches ignition on there at zero RPM, and then opens the same vehicle in Drive.

CONFIGURATION TRANSACTION

The local server validates candidate hardware and initial road conditions,
builds the candidate state and all UI resources, and serializes that response
before replacing the live session. Its resources match their GET counterparts
for all six supported vehicle types. Invalid options, invalid conditions,
resource preparation failure and serialization failure preserve the old model,
history, fault memory, diagnostic trace and active drive-cycle objects.

DOWNLOAD ACCEPTANCE PROCEDURE

The release download is built with:
  python3 tools/build_standalone.py --output ../OBDII_Release_0_9
The built file is checked separately from this source tree with:
  python3 tests/check_download.py --downloads ../OBDII_Release_0_9

That checker verifies embedded file hashes and a flat editable source archive;
launch from an otherwise empty directory with spaces; current application and
guide assets; configured driving, sensor faults and diagnostics through the
packaged API; a recorded WLTC run; repeated startup, port conflicts and cleanup.
Its launcher uses a browser-handoff recorder, not a native GUI browser.

VERIFICATION LIMITS

Frontend checks use actual application JavaScript and actual Python model/API
data with a parsed-node harness and CPU Canvas. They do not establish native
browser layout, native event behavior or GPU rendering. Native browser launch
was unavailable in this environment. The user's Linux Mint installation has
not been tested directly. The 31 checks in START_HERE.txt and docs/WORKSPACE.html
are the practical local acceptance sequence.

The virtual vehicle remains a generic teaching model. Individual OEM ECU
firmware, complete actuator circuits, real CAN bit timing and a real diagnostic
adapter are not implemented by this workflow update.
