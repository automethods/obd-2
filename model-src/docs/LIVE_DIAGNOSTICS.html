OBD II Lab · interactive diagnostic desk

From a question to a readable value.

Open Protocols & scan tool in the workbench. The desk links a request, its connector path, the generated CAN frames and the decoded answer. Every result comes from the simulator’s diagnostic callback.

Return to the lab

1. Read a value and replay its route

  1. Open Live requests and choose Engine speed. The lab sends 01 0C to its engine ECU.
  2. Read the large sampled value and the application bytes. The timestamp identifies when the request sampled the model. Changing an input does not rewrite a past reply; ask again for a fresh reading.
  3. Press Replay. Six steps show the question, connection, request frame, ECU service, return path and decoded result. Use Pause replay, Next step or a numbered step to inspect it.
  4. Select a row in the CAN / ISO-TP frame trace. The byte inspector separates transport information, application bytes and padding.
Two clocks have different jobs.

Run / Pause controls the simulated vehicle. Replay uses a deliberately slow presentation clock so you can read the explanation. It does not send a second request, change the ECU or advance the simulated vehicle. Reduced-motion preferences disable automatic replay motion; numbered steps remain available.

2. Read the calculation

The decoder uses the returned bytes. It does not substitute current plant values if a response is missing.

RequestValueApplication responseCalculation
01 0CEngine speed41 0C A B(256 × A + B) ÷ 4 rpm
01 05Reported coolant41 05 AA − 40 °C
01 0DVehicle speed41 0D AA km/h
01 04Calculated load41 04 A100 × A ÷ 255 %

Here A and B are unsigned decimal interpretations of the data bytes. Response service 41 identifies a response to service 01; the next byte identifies the requested PID. The decoder displays both hex bytes and the substituted arithmetic.

The coolant experiment distinguishes the physical coolant, the sensor report and ECU fallback. Its disconnected sensor produces an invalid −40 °C marker. That marker is a diagnostic observation in this model, not the physical coolant temperature.

3. Inspect a long identity response

Choose Vehicle identity example under OBD, or Read synthetic VIN under UDS. The response contains a deliberately invented identity. In the trace, select each frame:

First Frame (FF)

The transport header gives the length of the complete application message. The rest of this frame begins the payload.

Flow Control (FC)

The receiver tells the sender to continue and supplies a block-size and separation-time field.

Consecutive Frames (CF)

Numbered fragments carry the remaining bytes. The inspector identifies their sequence header and any final padding.

Reassembled application

The desk then interprets the response service, the identifier and the ASCII text. Transport headers and padding are not part of the identity.

4. Explore the connector and layers

Open Connector & layers. The connector drawing looks into the female vehicle socket: 1–8 across the upper row and 9–16 across the lower row. Choose CAN or one of the legacy reference families to highlight its contact roles. Select any numbered contact for its meaning and model scope.

The seven-layer teaching map lets you separate the physical contacts, CAN frames, ISO-TP transport, addressing and diagnostic meaning. Standards can cover several responsibilities. The map does not assert seven independent protocols or complete OSI-layer implementations.

5. Understand the implemented scope

Protocol reference marks each family as a runnable subset or reference material. The runnable examples are selected OBD services over CAN and the declared UDS session/identification subset. ISO 9141-2, KWP2000, J1850, DoIP and LIN are explanations only. No legacy electrical initialization, Ethernet endpoint, production ECU, security unlocking or flashing is included.

The module catalog links to the machine-readable diagnostic definitions. Only modules with implemented diagnostic services receive request definitions and addresses. The battery, hybrid and brake controller observations remain available through model state and wire probes without inventing diagnostic responses.

6. Suggested comparisons

  1. Read engine speed twice, with a changed accelerator input and a simulation step between requests. Compare the bytes and arithmetic.
  2. Disconnect the diagnostic branch and repeat the same request. No reply must remain unavailable rather than turning into zero.
  3. Reconnect, then request a VIN. Inspect FF, FC and CF and compare their byte roles.
  4. Run the coolant fault experiment. Compare the physical coolant with the OBD report and stored warning memory.
  5. In the layer map, select Application, Transport and Physical while viewing the same captured result.

Sources and design references

The interactive artwork and writing were created for this lab. The references supplied by the user guided the emphasis on readable dashboard values, clear connector diagrams and a visible relationship between bytes and signals.

  • Elm Electronics ELM327 datasheet — request examples and vehicle connector/interface diagrams.
  • Linux kernel ISO-TP documentation — addressing, frame types and transport behavior.
  • CSS Electronics OBD introduction — user-supplied visual reference.
  • SimpleOBDII repository — user-supplied example of an expandable diagnostic application.
  • CSS Electronics signal-discovery article — user-supplied example of comparing raw fields with a reference. This lab performs no automatic reverse engineering.
All vehicle values and identities in the lab are synthetic. A frame transcript is an explanation of the implemented diagnostic exchange, not a captured physical bus waveform.
